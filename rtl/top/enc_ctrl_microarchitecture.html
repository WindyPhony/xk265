Block-level description

enc_ctrl is a pipeline sequencer and CTU progress tracker. It does not process pixels. Its job is to:

  1. Accept a frame-level start (sys_start_i) and frame parameters (sys_type_i, sys_ctu_all_x_i, sys_ctu_all_y_i).
  2. Progressively activate (ramp-up) and then deactivate (drain) encoder sub-blocks as a pipeline, advancing one CTU position per pipeline step.
  3. Track completion of each sub-block and advance the pipeline when all expected completions for the current stage are satisfied.
  4. Drive CTU x/y coordinates to every sub-block through a cascading register pipeline.
  5. Drive fetch enable/address signals to the data memory interface (fetch_top).
  6. Signal frame completion (sys_done_o) when the last CTU exits the pipeline.

4.4 Key Architectural Insight: S5 Loop

State S5 is the sustained pipeline state. While the pipeline is full, the FSM stays in S5. Each time all 6 expected flags are set, enc_done_r pulses, advancing all coordinate registers one CTU forward, and the cycle repeats. The FSM only leaves S5 when the last CTU (pre_l_x == sys_ctu_all_x && pre_l_y == sys_ctu_all_y) has been processed.

5. FSM State-by-State Behavioral Analysis

IDLE (State 0)
  • Purpose: Wait for frame start command.
  • Entry condition: Reset, or after SA completes.
  • Exit condition: sys_start_i == 1 → transition to S0.
  • Controlled modules: None. All enables = 0.
  • Registers updated: cur_state holds IDLE. Coordinate registers hold 0. Flags cleared (line 405–413).
  • Next states: S0 (if sys_start_i), else IDLE.
  • RTL evidence: Lines 285, 274, 308, 405–413.
S0 (State 1) — Fetch / Pre-load of first CTU
  • Purpose: Kick off fetch for CTU at (0,0); begin pre-load of luma data.
  • Entry condition: sys_start_i was asserted last cycle.
  • Exit condition: enc_start_w == 1 (i.e. fetch_flg is set, as S0 expects only fetch done).
  • Controlled modules: fetch_top (via load_cur_luma_ena_o), pre_l pipeline.
  • Important control signals: pre_l_ena = 1; all others = 0.
  • enc_done_r expected: {fetch_flg, stg_1_flg, stg_2_flg, rec_flg, db_flg, ec_flg} == 6'b1_000_00
  • Registers updated on enc_done_r: All coordinate registers shift. pre_l_x_o/y_o advance to next CTU.
  • Next states: S1 (when enc_done_r fires).
  • RTL evidence: Lines 286, 308, 449.
S1 (State 2) — Pipeline stage-1 enters (PREI or IME)
  • Purpose: Activate first encoder processing stage (PREI for INTRA, or IME for INTER) on the next CTU, while pre_l continues.
  • Exit condition: fetch_flg && stg_1_flg.
  • Controlled modules: fetch, PREI (always), IME (INTER only).
  • enc_done_r expected: 6'b1_100_00
  • Next states: S2.
  • RTL evidence: Lines 287, 309, 450, 324–327.
S2 (State 3) — Pipeline stage-2 enters (POSI or FME)
  • Purpose: Activate second encoder stage (POSI for INTRA, or FME for INTER) on the third CTU.
  • Exit condition: fetch_flg && stg_1_flg && stg_2_flg.
  • Controlled modules: fetch, PREI, IME, POSI, FME.
  • enc_done_r expected: 6'b1_110_00
  • Next states: S3.
  • RTL evidence: Lines 288, 310, 451, 325, 328.
S3 (State 4) — Reconstruction enters
  • Purpose: Activate REC on the fourth CTU. Pipeline now has: pre_l → stg1 → stg2 → rec.
  • Exit condition: fetch_flg && stg_1_flg && stg_2_flg && rec_flg.
  • enc_done_r expected: 6'b1_111_00
  • Next states: S4.
  • RTL evidence: Lines 289, 311, 452.
S4 (State 5) — Deblocking enters
  • Purpose: Activate DB/SAO on the fifth CTU.
  • Exit condition: fetch_flg && stg_1_flg && stg_2_flg && rec_flg && db_flg.
  • enc_done_r expected: 6'b1_111_10
  • Next states: S5.
  • RTL evidence: Lines 290, 312, 453.
S5 (State 6) — Full pipeline / Sustained CTU processing
  • Purpose: All pipeline stages active. This is the steady-state for bulk CTU processing. Each enc_done_r pulse advances one CTU.
  • Entry condition: Previous state S4 completes, or re-entry after CTU advance.
  • Exit condition (leave pipeline): enc_start_w==1 && pre_l_x==sys_ctu_all_x && pre_l_y==sys_ctu_all_y (last CTU in frame).
  • Re-entry condition: enc_start_w==1 but not at last CTU → stay in S5.
  • Controlled modules: All: fetch, PREI, IME, POSI, FME, REC, DB, EC, store_DB.
  • enc_done_r expected: 6'b1_111_11 (all 6 flags set).
  • Important: EC and store_db are activated in S5; this is the first state where all 7 enables are high.
  • Next states: S6 (if last CTU) or S5 (if more CTUs remain).
  • RTL evidence: Lines 291–292, 313, 454.
S6 (State 7) — Pipeline drain: pre_l off
  • Purpose: No new CTU is loaded; remaining CTUs drain through the pipeline.
  • Exit condition: enc_start_w == 1.
  • enc_done_r expected: 6'b1_111_11 (all flags still high from the last batch).
  • Next states: S7.
  • RTL evidence: Lines 293, 314, 455.
S7 (State 8) — Pipeline drain: stg_1 off
  • Purpose: PREI/IME processing is finished for all CTUs.
  • enc_done_r expected: 6'b1_011_11 (stg_1_flg expected low — the stg_1 sub-blocks are done for this CTU and no new one was started).
  • Next states: S8.
  • RTL evidence: Lines 294, 315, 456.
S8 (State 9) — Pipeline drain: stg_2 off
  • Purpose: POSI/FME processing is finished for all CTUs.
  • enc_done_r expected: 6'b1_001_11
  • Next states: S9.
  • RTL evidence: Lines 295, 316, 457.
S9 (State 10) — Pipeline drain: rec off
  • Purpose: Reconstruction finished for all CTUs. Only DB, EC, store_db remain.
  • enc_done_r expected: 6'b1_000_11
  • Next states: SA.
  • RTL evidence: Lines 296, 317, 458.
SA (State 11) — Last stage drain: DB off, EC + store_db finish
  • Purpose: Final CTU exits the pipeline through EC and store_db. No new CTUs are started.
  • Exit condition: enc_done_r == 1.
  • enc_done_r expected: 6'b1_000_01 (only ec_flg expected; store_db done is implicitly covered by the pipeline structure).
  • sys_done_o: Asserted when cur_state==SA && nxt_state==IDLE (line 250). This is a one-cycle pulse at the very end.
  • Next states: IDLE.
  • RTL evidence: Lines 297, 318, 459, 250.

8.2 INTRA Mode Differences

When sys_type_i == INTRA (lines 530–546):

  • IME and FME are not started (ime_ena = 0, fme_ena = 0; lines 324–325).
  • ime_x_o/y_o and fme_x_o/y_o are forced to 0.
  • Stage-1 completion = prei_flg only (no ime_flg needed; line 437).
  • Stage-2 completion = posi_flg only (no fme_flg needed; line 438).
  • Coordinate flow: pre_l → prei → posi → rec → db → ec → store_db (IME/FME stages skipped).
  • Reference luma/chroma loads are disabled (lines 334, 336).

8.3 High-Level Sequence Description

  1. IDLE: Wait for sys_start_i.
  2. S0 (Ramp 1): Fetch first CTU luma. pre_l begins.
  3. S1 (Ramp 2): PREI/IME start on CTU 0. Fetch CTU 1.
  4. S2 (Ramp 3): POSI/FME start on CTU 0. PREI/IME on CTU 1. Fetch CTU 2.
  5. S3 (Ramp 4): REC on CTU 0. Pipeline depth = 4.
  6. S4 (Ramp 5): DB on CTU 0. Pipeline depth = 5.
  7. S5 (Full / Steady state): EC and store_db join. All 7 stages active. Each cycle advances one CTU. Loop continues until last CTU.
  8. S6–SA (Drain): Pipeline drains: pre_l off → stg1 off → stg2 off → rec off → DB off → EC+store_db finish.
  9. IDLE: sys_done_o pulse emitted. Ready for next frame.

All 8 flags are cleared simultaneously on either:

12. Microarchitecture Reconstruction

12.1 Control Path

  • FSM: 12-state sequential controller. State register: cur_state [3:0]. Asynchronous active-low reset to IDLE.
  • Next-state logic: Purely combinational (lines 281–299). Depends on cur_state, enc_start_w (= enc_done_r), sys_start_i, and CTU position comparison.
  • Enable generation: Combinational decode of cur_state into 7-bit enable vector (lines 304–322).
  • Start generation: All start outputs are registered from enable bits, gated by enc_start_o (lines 356–390). This creates a one-cycle pulse delay after enable assertion.
  • Done detection: Sticky flags accumulate done_i pulses. Combined flags checked per-state for expected pattern. Registered pulse generated as enc_done_r (lines 442–462).
  • No arbitration: The controller is purely sequential — one CTU at a time, no resource contention management.

12.2 Datapath Interaction

  • enc_ctrl does NOT process data. It only generates control signals (start, coordinates, enables) and monitors completion signals.
  • Coordinate cascade: 8 pairs of registered x/y values form a pipeline delay chain, ensuring each sub-block receives the coordinate of the CTU it should be processing.
  • INTRA vs INTER switching: Single mux on sys_type_i controls:
    • Whether IME/FME are activated (lines 324–325)
    • How stage completion flags are combined (lines 437–438)
    • How coordinates cascade through the pipeline (lines 530–566)
    • Which fetch enables are asserted (lines 332–351)

12.3 Memory Interaction

  • enc_ctrl drives fetch enables and addresses but does not directly control any memory.
  • Fetch enable guards:
    • load_db_*_ena suppressed when rec_y_o == 0 (first row, no top neighbor).
    • store_db_*_ena suppressed when store_db_x_o == 0 (first column, leftmost CTU delayed by 3 DB memories).
  • These guards are implemented as combinational conditions on the enable outputs (lines 337–340, 347–350).

12.4 Pipeline Interaction

  • enc_ctrl implements a linear pipeline controller. It is NOT a general-purpose pipeline — it is a fixed 7-stage pipeline where each stage corresponds to a specific sub-block.
  • No overlap between CTUs within a stage: Each sub-block receives exactly one start pulse per CTU. The next CTU's start pulse only arrives after the current CTU's done flag is latched.
  • Full overlap across stages: Up to 7 CTUs are in flight simultaneously (one per pipeline stage) once the pipeline is full.
  • No backpressure: The controller waits for all expected completions before advancing; there is no mechanism for a sub-block to signal "busy" or "not ready."

16. Potential Bottlenecks

  1. Ramp-up latency: 5 cycles of pipeline fill before all stages are active. For small pictures this is significant relative to total processing time. INFERRED from S0–S4 enable progression
  2. Drain latency: 5 cycles to fully drain the pipeline after the last CTU. INFERRED from S6–SA enable regression
  3. No inter-frame overlap: The next frame cannot start until the current frame is fully drained (S6→SA→IDLE→sys_start_i). VERIFIED from lines 250, 297
  4. No CTU-level parallelism within a sub-block: Each sub-block processes one CTU at a time; the controller does not support multiple CTUs in the same stage. INFERRED from single start pulse per stage per CTU
  5. Store_db column-0 suppression: The leftmost CTU in each row cannot store DB results, introducing a 1-CTU bubble at each row boundary. VERIFIED from lines 339–340, 349–350
  6. Load_db row-0 suppression: The topmost CTU row cannot load DB reference data, potentially stalling the DB stage. VERIFIED from lines 337–338, 347–348

19. Final Microarchitecture Summary

A. Controller Role

enc_ctrl is the central pipeline sequencer and CTU progress controller for the xk265 HEVC encoder. It does not process data. It sequences sub-block execution through a 7-stage fixed pipeline, advances CTU coordinates, and manages frame-level start/done handshakes with the top level.

B. FSM

12 states: IDLE → S0 → S1 → S2 → S3 → S4 → S5 (loop) → S6 → S7 → S8 → S9 → SA → IDLE.

  • S0–S4: Ramp-up — progressively enabling pipeline stages.
  • S5: Steady state — all 7 stages active, loop over all CTUs.
  • S6–SA: Drain — progressively disabling pipeline stages.

C. Control Flow

  1. Wait for sys_start_i in IDLE.
  2. Ramp up: enable one additional pipeline stage per state (S0→S5).
  3. At S5, loop: for each CTU, wait for all expected completions → advance → repeat.
  4. On last CTU, drain: S5→S6→…→SA→IDLE.
  5. Pulse sys_done_o.

D. Datapath Interaction

enc_ctrl drives 8 start pulses, 8 pairs of CTU coordinates, and 8 fetch enable+address signals to downstream sub-blocks. It monitors 8 done signals and uses sticky flags + pattern matching to determine when to advance the pipeline. It does not touch pixel data, coefficients, or bitstream bits.

E. Timing

  • Ramp-up: 5 state transitions (S0–S4) before pipeline is full.
  • Steady-state: 1 CTU per enc_done_r pulse (latency depends on sub-blocks).
  • Drain: 5 state transitions (S6–SA) after last CTU.
  • Exact per-CTU latency: UNKNOWN from enc_ctrl.v alone.

F. Bottlenecks

  • 5-cycle ramp-up + 5-cycle drain overhead per frame.
  • No inter-frame pipelining (must fully drain before next frame).
  • store_db column-0 suppression: 1-CTU stall per row.
  • load_db row-0 suppression: potential stall for top-row CTUs.

G. Unknowns

  • Exact sub-block latencies (all 8 sub-blocks).
  • Internal sub-block handshakes and data widths.
  • CU/PU/TU partitioning within each CTU (handled inside sub-blocks).
  • Bitstream output collection and buffering.
  • Reference buffer (DPB) management.
  • Whether sys_type_i can vary per-frame or is fixed for entire encode.
  • Behavior when done_i pulses arrive out-of-order or with variable latency across sub-blocks.
